### The one that mattered most

`3d545f3`. AmigaOS HUNK executables have no entry-point field: execution begins at the
first byte of the first hunk. `novus_ffi_runtime.o` was being linked ahead of
`novus_startup.o`, so `___novus_ffi_init` sat at CODE+0 and `_start` at 0x24. Every
binary built after the FFI regeneration ran the init stub and returned immediately with
`d0=1`. `main` never ran. `rc=1` was literally ffi_init's success value.

Everything else in the session was found downstream of fixing that.

## Open bug 1 — device example, address error at `-O=1`

**Symptom**

```
Software Failure
SYS:Barry/o3suite/p_device-example_O1
Program failed (error #80000003)
```

`#80000003` is a 68k address error — odd-address access on a word or long.

**What is established**

- `-O=1` build crashes. `-O=3` build of the same source runs perfectly: full
  `CMD_RESET` / `CMD_CONFIG` / `CMD_STATUS` sequence, rc=0.
- Not a device/example mismatch. First observed with the `-O=1` example against the
  `-O=3` device; reinstalled the matching `-O=1` device and it crashed identically.
  The `-O=1` example fails against *both* devices, so the fault is on the example side.
- Debug build of the same example works — verified earlier the same day.

**Theory**

Something in the release path lands a struct or IORequest field on an odd address, or
reads one through a misaligned pointer. `-O=1` and `-O=3` differ in vbcc register
allocation, so this is likely a latent alignment assumption that only one allocation
exposes. Note the example builds an `IOStdReq` and passes pointers into exec —
`mn_Length`, `io_Message`, and friends are all word/long fields where an odd base would
fault exactly like this.

Release also differs from debug in **safety level**, not just optimization: debug
defaults to 2, release to 1. That changes generated code (bounds checks, MMU
protection). **This has not been ruled out and should be tested first** — it is cheaper
than an assembly diff:

```sh
novus build --release --safety-level 2     # if this fixes it, it is not -O at all
```

**Next step**

1. Try `--release --safety-level 2`. If it passes, the bug is safety-level-dependent,
   not optimization-dependent, and the whole `-O` framing is wrong.
2. If not, diff generated C between `-O=1` and `-O=3` for the device example. When this
   was done for `Args::parse` the C came out byte-identical, which proved the problem
   was vbcc and not our IR — the same test is worth one command here.
3. If the C is identical, get the faulting PC via `arm_crash_trapping` + `crash_report`,
   then `Za <addr>` to resolve it to a `.novus` line. The debug-symbol chain works end
   to end now (see below), so this should land on a source line directly.

## Open bug 2 — gui-modern broken in release

**Symptom**

- `-O=1`: running it **hard-resets the machine**. Reproduced twice; the second time in
  isolation with nothing else running.
- `-O=3`: no window ever appears. Confirmed with a 12-second wait, so not a timing
  artifact. Exit code 10 from `wrun`, meaning the window never showed up.
- Debug: works. Window opens with a functioning Close gadget, verified earlier.

`gui-traditional` passes at `-O=1` and `-O=3`. So this is specific to the "modern"
(ReAction/GadTools) template, not to windowed programs generally.

**Theory**

The modern template drives more of the FFI surface — GadTools/ReAction classes, tag
lists, BOOPSI objects. A machine reset rather than a Guru suggests memory corruption
rather than a simple bad pointer: something scribbling over exec structures. A tag list
terminated wrongly, or a `NewObject` argument array that is not what the class expects,
would do it.

That the `-O=3` failure is *silent* (no window, no crash) hints the two levels are
failing at different points in the same broken setup path, not at two unrelated bugs.

**Next step**

Same order as bug 1: try `--safety-level 2` first, then compare generated C between
levels, then trap the crash. For the reset case, `arm_crash_trapping` with the default
mask before launching is essential — otherwise the machine is gone before anything is
readable.

## What is implemented and working

**Debug symbols, end to end.** `.novus` file and line reach the debugger. Verified by
independent parse and by FS-UAE agreeing:

```
Za 047b2782
  047b2782: 'SYS:Barry/spinner2' #00 [...] +00000282
      047b2760 +00000022  _inner_work
                          spinner.novus:6
```

Debug builds carry `HUNK_SYMBOL` + `HUNK_DEBUG`/'LINE'; release strips both. This
needed three fixes on the FS-UAE side (not this repo) plus the epilogue-anchoring fix
in `6e80ef3`.

**Test harness.** See `tools/amiga/README.md`. Short version:

- CLI-only programs: `vamos -C 68020 -- <prog>` on the host, ~1s, no emulator.
  **The `-C 68020` is mandatory** — vamos defaults to 68000 and dies at an odd PC on
  our binaries, which looks exactly like a codegen bug and is not one.
- `.library` / `.device` / anything windowed: FS-UAE.
- Windowed programs: `wrun <prog> [seconds]` — launches, verifies the window appeared,
  closes it, hands focus back. Without it, every GUI test costs a reboot.
- Whole suites: an AmigaDOS script plus one `Execute`. **Redirect each test to its own
  file.** A crashing test leaves its output unflushed, so a shared stream loses
  everything from the crash onward — this was misread as a harness truncation bug for a
  while.
- `FailAt 100` at the top of any suite script, or the shell aborts on the first rc>=10
  and legitimate non-zero results (the library example returns 36 by design) kill the run.

**Toolchain is now pinned.** `vc` resolves `vbccm68k`/`vasmm68k_mot`/`vlink` through
PATH, not `$VBCC`. Before `db7f8fc`, a vbcc elsewhere on PATH silently compiled the
build — which is why a fix made in `vendor/vbcc` appeared to do nothing. Any future
vendored-toolchain change depends on that pinning staying in place.

## What is not implemented

- **The two crashes above.** Not fixed, not worked around.
- **`-O` default.** Left at `-O=1`. Was going to move to `-O=3` (smallest, and correct
  after the vbcc fix) until the hardware run showed `-O=1` crashing the device example
  and `-O=3` silently failing gui-modern. Do not move it on size evidence alone.
- **workbench-traditional / workbench-modern on hardware.** Never run at `-O=1` or
  `-O=3`. They are the same templates as gui-\*, so workbench-modern is expected to
  behave like gui-modern, but that is an assumption, not a measurement.
- **library example at `-O=3`.** Not run. `-O=1` passes (rc=36).
- **Amiga tests in CI.** CI runs two C# test classes in a Linux container — no vbcc, no
  emulator, nothing Amiga-side. vamos is the realistic path if that is ever wanted;
  FS-UAE needs ROMs and a 2-minute boot.
- **Speed measurements.** Every optimization decision so far is on binary size only.

## Things worth not relearning

- **Verify the artifact came from the toolchain before diagnosing the toolchain.** A
  whole analysis earlier in the session was built on `th_Pellets`, which turned out to
  be from a CMake C project that had never touched Novus. Everything downstream of that
  was wrong.
- **vamos disagreeing with hardware is a signal, not noise.** It flagged `Args::parse`
  as broken while the A4000 ran it fine. vamos was right — the hardware was passing on a
  stale condition-code value that happened to be favourable. That turned into the vbcc
  peephole fix. Keep the second implementation around precisely so it can disagree.
- **`-debug=512` masks the vbcc bug.** The extra emits perturb register allocation, so
  the failing sequence does not reproduce under the debug flag. And `-no-peephole` does
  not disable the emit-level peephole; only `-old-peephole` does.
- **A Guru is not always the program under test.** `wrun` blew the 4K CLI stack and
  crashed mid-batch, which briefly looked like a Novus failure. Novus binaries carry a
  `$STACK:` cookie and were never exposed to it; hand-written C tools are.
