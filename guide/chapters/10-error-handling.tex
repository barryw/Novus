\chapter{Error Handling}
\label{ch:error-handling}

\begin{quote}
\textit{``Errors should never pass silently. Unless explicitly silenced.''} --- The Zen of Python
\end{quote}

Novus treats errors as values, not exceptions. Every operation that can fail returns a \texttt{Result} type, making error handling explicit and impossible to ignore. This chapter covers Novus's error handling philosophy, the standard error types, and patterns for writing robust code.

% ============================================================================
\section{Philosophy: Errors as Values}
\label{sec:error-philosophy}
% ============================================================================

Unlike languages with exceptions, Novus requires explicit handling of errors:

\begin{itemize}
    \item \textbf{No hidden control flow} --- You always know when a function can fail
    \item \textbf{No uncaught exceptions} --- Errors can't silently propagate up the stack
    \item \textbf{Compile-time enforcement} --- Ignoring a \texttt{Result} produces a warning
    \item \textbf{Zero runtime cost} --- No exception tables or unwinding machinery
\end{itemize}

\subsection{Why Not Exceptions?}

Many languages use exceptions for error handling. While convenient in some ways, exceptions have significant drawbacks for systems programming:

\textbf{1. Stack Unwinding Cost:}
Exception handling requires runtime machinery to unwind the stack, search for handlers, and call destructors. On a 68020 running at 14 MHz, this overhead is unacceptable.

\textbf{2. Invisible Control Flow:}
Any function call might throw, making control flow analysis difficult. In Novus, functions that can fail are marked by their return type.

\textbf{3. Unpredictable Cleanup:}
With exceptions, you need \texttt{try/finally} blocks to ensure resources are released. In Novus, \texttt{Result} combinators and pattern matching make cleanup explicit.

\textbf{4. Binary Size:}
Exception tables and unwinding code add significant size to executables. Every byte counts on classic Amiga systems.

\subsection{Why Not errno?}

The traditional C approach of global error codes has its own problems:

\begin{lstlisting}[language=C]
// C with errno
FILE *f = fopen("data.txt", "r");
if (f == NULL) {
    if (errno == ENOENT) { /* not found */ }
    else if (errno == EACCES) { /* permission denied */ }
    // Easy to forget, hard to get right
}
\end{lstlisting}

\textbf{Problems with errno:}
\begin{itemize}
    \item Global mutable state is inherently error-prone
    \item Easy to forget to check it
    \item Can be overwritten by intermediate calls
    \item Not type-safe --- any integer could be assigned
    \item Thread-unsafe without special handling
\end{itemize}

AmigaOS uses a similar pattern with \texttt{IoErr()}:

\begin{lstlisting}[language=C]
// AmigaOS with IoErr()
BPTR lock = Lock("myfile", ACCESS_READ);
if (lock == 0) {
    LONG err = IoErr();  // Must call immediately!
    // But what if you call something else first?
    PrintFault(err, "Error");
}
\end{lstlisting}

The danger: if you call \emph{any} other DOS function before \texttt{IoErr()}, the error code may be overwritten.

\begin{comingfromc}
In C, errors are typically indicated by return values (\texttt{-1}, \texttt{NULL}) or global \texttt{errno}/\texttt{IoErr()}. This leads to bugs when callers forget to check.

In Novus, \texttt{Result<T, E>} forces you to handle both success and failure cases. You cannot accidentally use an error value as if it were successful.

\begin{center}
\begin{tabular}{ll}
\textbf{C (AmigaOS)} & \textbf{Novus} \\
\hline
\texttt{if (ptr == NULL)} & \texttt{match result \{ ... \}} \\
\texttt{if (fd < 0)} & \texttt{let file = open(path)?} \\
\texttt{IoErr()} & \texttt{Result::Err(DosError::NotFound)} \\
Manual conversion & \texttt{From} trait auto-conversion \\
\end{tabular}
\end{center}
\end{comingfromc}

% ============================================================================
\section{The Result Type}
\label{sec:result-type}
% ============================================================================

The core error handling type is \texttt{Result<T, E>}:

\begin{lstlisting}
enum Result<T, E> {
    Ok(T),    // Success with value
    Err(E),   // Failure with error
}
\end{lstlisting}

Every function that can fail returns a \texttt{Result}:

\begin{lstlisting}
fn parse_number(s: *u8) -> Result<i32, ParseError> {
    // Returns Ok(value) or Err(error)
}

fn open_file(path: *u8) -> Result<FileHandle, DosError> {
    // Returns Ok(handle) or Err(error)
}
\end{lstlisting}

\subsection{Result Methods Reference}

The \texttt{Result} type provides several methods for working with values:

\begin{center}
\begin{tabular}{lp{8cm}}
\textbf{Method} & \textbf{Description} \\
\hline
\texttt{is\_ok()} & Returns \texttt{true} if the result is \texttt{Ok} \\
\texttt{is\_err()} & Returns \texttt{true} if the result is \texttt{Err} \\
\texttt{unwrap()} & Extracts the \texttt{Ok} value, panics on \texttt{Err} \\
\texttt{unwrap\_or(default)} & Returns the \texttt{Ok} value or the provided default \\
\texttt{expect(msg)} & Like \texttt{unwrap()} but with a custom panic message \\
\texttt{ok()} & Converts to \texttt{Option<T>}, discarding the error \\
\texttt{err()} & Converts to \texttt{Option<E>}, discarding the success value \\
\end{tabular}
\end{center}

\begin{lstlisting}
let result: Result<i32, Error> = some_operation()

// Query the state
if result.is_ok() {
    println("Operation succeeded")
}

// Get value with default
let value = result.unwrap_or(0)

// Convert to Option
let maybe_value: Option<i32> = result.ok()
\end{lstlisting}

% ============================================================================
\section{The Option Type}
\label{sec:option-type}
% ============================================================================

While \texttt{Result} represents success or failure, \texttt{Option} represents presence or absence:

\begin{lstlisting}
enum Option<T> {
    Some(T),  // Value present
    None,     // No value
}
\end{lstlisting}

\subsection{When to Use Option vs Result}

\begin{itemize}
    \item Use \textbf{Option} when the only failure mode is ``not found'' or ``not available''
    \item Use \textbf{Result} when there are multiple failure modes to distinguish
    \item Use \textbf{Result} for operations that interact with the OS or hardware
\end{itemize}

\begin{lstlisting}
// Option: "not found" is the only failure
fn find_user(id: u32) -> Option<User> { ... }

// Result: multiple failure modes possible
fn load_user(id: u32) -> Result<User, DbError> { ... }
\end{lstlisting}

\subsection{Option Methods Reference}

\begin{center}
\begin{tabular}{lp{8cm}}
\textbf{Method} & \textbf{Description} \\
\hline
\texttt{is\_some()} & Returns \texttt{true} if value is present \\
\texttt{is\_none()} & Returns \texttt{true} if no value \\
\texttt{unwrap()} & Extracts the value, panics on \texttt{None} \\
\texttt{unwrap\_or(default)} & Returns value or provided default \\
\texttt{expect(msg)} & Like \texttt{unwrap()} with custom panic message \\
\end{tabular}
\end{center}

\subsection{Converting Between Option and Result}

Sometimes you need to convert between the two types:

\begin{lstlisting}
// Option -> Result: provide an error for None
fn get_config_value(key: *u8) -> Result<*u8, ConfigError> {
    match config.get(key) {
        Option::Some(val) => Result::Ok(val),
        Option::None => Result::Err(ConfigError::MissingKey)
    }
}
\end{lstlisting}

\begin{comingfromc}
In C, null pointers serve double duty: representing ``no value'' (Option) and ``error occurred'' (Result). This conflation causes bugs.

\begin{lstlisting}[language=C]
// C: Is NULL "not found" or "error"?
Node *node = find_node(list, key);
if (node == NULL) {
    // Did find fail, or is the key just missing?
    // Have to check errno to know...
}
\end{lstlisting}

In Novus, the type system distinguishes these cases. \texttt{Option<T>} means ``might not exist'' while \texttt{Result<T, E>} means ``might have failed''.
\end{comingfromc}

\section{The ? Operator In Depth}
\label{sec:question-operator}
% ============================================================================

The \texttt{?} operator is syntactic sugar for early return on error. It transforms verbose error checking into concise, readable code.

\subsection{What ? Actually Does}

When you write:
\begin{lstlisting}
let file = open_file(path)?
\end{lstlisting}

The compiler generates equivalent code to:
\begin{lstlisting}
let file = match open_file(path) {
    Result::Ok(val) => val,
    Result::Err(e) => return Result::Err(e)
}
\end{lstlisting}

The \texttt{?} operator:
\begin{enumerate}
    \item Checks if the result is \texttt{Err}
    \item If \texttt{Err}, returns immediately with that error
    \item If \texttt{Ok}, unwraps the value and continues
\end{enumerate}

\subsection{Chaining Multiple ? Calls}

The real power of \texttt{?} shows when chaining fallible operations:

\begin{lstlisting}
fn process_file(path: *u8) -> Result<Data, DosError> {
    let file = open_file(path)?       // Returns Err early if failed
    let header = read_header(&file)?  // Returns Err early if failed
    let body = read_body(&file)?      // Returns Err early if failed
    let data = parse_data(&body)?     // Returns Err early if failed
    Result::Ok(data)
}
\end{lstlisting}

Without \texttt{?}, this would require deeply nested match statements:

\begin{lstlisting}
fn process_file(path: *u8) -> Result<Data, DosError> {
    match open_file(path) {
        Result::Ok(file) => {
            match read_header(&file) {
                Result::Ok(header) => {
                    match read_body(&file) {
                        Result::Ok(body) => {
                            match parse_data(&body) {
                                Result::Ok(data) => Result::Ok(data),
                                Result::Err(e) => Result::Err(e)
                            }
                        },
                        Result::Err(e) => Result::Err(e)
                    }
                },
                Result::Err(e) => Result::Err(e)
            }
        },
        Result::Err(e) => Result::Err(e)
    }
}
\end{lstlisting}

\subsection{Using ? in main()}

In Novus, \texttt{main()} returns \texttt{i32} (the exit code). You can still use \texttt{?} by wrapping your logic:

\begin{lstlisting}
fn run() -> Result<(), AppError> {
    let config = load_config()?
    let window = open_window()?
    main_loop(&window)?
    Result::Ok(())
}

pub fn main() -> i32 {
    match run() {
        Result::Ok(_) => return 0,
        Result::Err(err) => {
            println(err.message())
            return 1
        }
    }
}
\end{lstlisting}

\subsection{Limitations of ?}

The \texttt{?} operator can only be used in functions that return \texttt{Result}:

\begin{lstlisting}
fn valid() -> Result<(), Error> {
    let x = fallible_op()?  // OK: function returns Result
    Result::Ok(())
}

fn invalid() {
    let x = fallible_op()?  // ERROR: function doesn't return Result
}
\end{lstlisting}

When a function may fail with errors from multiple subsystems, use \texttt{NovusError}:

pub enum NovusError {

\begin{lstlisting}
fn load_and_display(path: *u8) -> Result<(), NovusError> {
    let data = read_file(path)?       // DosError -> NovusError
    let screen = open_screen()?       // IntuitionError -> NovusError
    let bitmap = load_bitmap(&data)?  // GraphicsError -> NovusError
    display(screen, bitmap)
    Result::Ok(())
}
\end{lstlisting}

\section{Error Conversion with From}
\label{sec:error-conversion}
% ============================================================================

The \texttt{From} trait enables automatic error type conversion when using \texttt{?}:

\begin{lstlisting}
trait From<T> {
    fn convert(value: T) -> Self
}
\end{lstlisting}

When you use \texttt{?} in a function returning \texttt{Result<T, NovusError>}, and the inner call returns \texttt{Result<T, DosError>}, the compiler automatically calls \texttt{NovusError::From<DosError>::convert()} to wrap the error.

\subsection{Manual Conversion}

You can also convert errors manually:

\begin{lstlisting}
from std::error::errors import novus_error_from_dos

fn wrapper() -> Result<(), NovusError> {
    let file = match open("file.txt", MODE_OLDFILE) {
        Result::Ok(f) => f,
        Result::Err(e) => return Result::Err(novus_error_from_dos(e))
    }
    Result::Ok(())
}
\end{lstlisting}

\subsection{Getting Raw Error Codes}

For debugging or interop with C code, get raw AmigaOS error codes:

\begin{lstlisting}
from std::error::errors import dos_error_to_code

let code = dos_error_to_code(DosError::NotFound)  // Returns 205
\end{lstlisting}

\section{Error Handling Patterns}
\label{sec:error-patterns}
% ============================================================================

This section covers common patterns for handling errors effectively.

\subsection{Early Return Pattern}

Validate inputs at the start of a function and return errors immediately. This keeps the main logic clean:

\begin{lstlisting}
fn process(data: *u8, len: u32) -> Result<(), Error> {
    // Validate all inputs first
    if data == null {
        return Result::Err(Error::InvalidInput)
    }
    if len == 0 {
        return Result::Err(Error::EmptyData)
    }
    if len > MAX_SIZE {
        return Result::Err(Error::TooLarge)
    }

    // All validation passed - main logic here
    do_actual_work(data, len)
}
\end{lstlisting}

\begin{comingfromc}
In C, you often see scattered validation throughout functions:

\begin{lstlisting}[language=C]
int process(char *data, size_t len) {
    int result = init_something();
    if (result < 0) return result;

    if (data == NULL) return -EINVAL;  // Mixed with logic!

    result = do_more_work();
    if (result < 0) goto cleanup;

    if (len == 0) goto cleanup;  // Validation too late!
    // ...
}
\end{lstlisting}

The early return pattern in Novus collects all validation at the top, making the ``happy path'' obvious.
\end{comingfromc}

\subsection{Fallback Chains}

Try multiple approaches, falling back on failure. This is common for finding configuration files or resources:

\begin{lstlisting}
fn find_config() -> Result<Config, ConfigError> {
    // Try user config first
    match load_from("ENV:app.cfg") {
        Result::Ok(cfg) => return Result::Ok(cfg),
        Result::Err(_) => {}
    }

    // Fall back to archive
    match load_from("ENVARC:app.cfg") {
        Result::Ok(cfg) => return Result::Ok(cfg),
        Result::Err(_) => {}
    }

    // Fall back to system config
    match load_from("S:app.cfg") {
        Result::Ok(cfg) => return Result::Ok(cfg),
        Result::Err(_) => {}
    }

    // Use defaults as last resort
    Result::Ok(default_config())
}
\end{lstlisting}

\subsection{Cleanup on Error with defer}

Use \texttt{defer} to ensure cleanup even when returning early on error:

\begin{lstlisting}
fn process_file(path: *u8) -> Result<Data, DosError> {
    let file = open(path, MODE_OLDFILE)?
    defer { close(file) }  // Always runs, even on error return

    let header = read_header(&file)?  // May return early
    let body = read_body(&file)?      // May return early

    Result::Ok(combine(header, body))
    // defer runs here on success too
}
\end{lstlisting}

\subsection{Error Context}

Add context when propagating errors by matching and re-wrapping with domain-specific information:

\begin{lstlisting}
fn load_user_config() -> Result<Config, ConfigError> {
    let path = get_config_path()?

    let file = match open(path, MODE_OLDFILE) {
        Result::Ok(f) => f,
        Result::Err(_) => return Result::Err(ConfigError::FileNotFound)
    }

    let data = match read_all(&file) {
        Result::Ok(d) => d,
        Result::Err(_) => return Result::Err(ConfigError::ReadFailed)
    }

    parse_config(&data)
}
\end{lstlisting}

\subsection{Retry Pattern}

For transient failures (disk not ready, network timeout), retry a few times:

\begin{lstlisting}
fn open_with_retry(path: *u8, max_retries: u32) -> Result<FileHandle, DosError> {
    var attempts: u32 = 0

    while attempts < max_retries {
        match open(path, MODE_OLDFILE) {
            Result::Ok(file) => return Result::Ok(file),
            Result::Err(DosError::NoDisk) => {
                // Disk not ready - wait and retry
                delay(Duration::from_secs(1))
                attempts = attempts + 1u32
            },
            Result::Err(e) => return Result::Err(e)  // Non-retriable
        }
    }

    Result::Err(DosError::NoDisk)
}
\end{lstlisting}

\section{Panic: When Errors Are Bugs}
\label{sec:panic}
% ============================================================================

A \textbf{panic} is for situations where continuing is impossible---invariant violations, impossible states, or programmer errors.

\begin{lstlisting}
// Panic on invariant violation
fn get_first(vec: &Vec<i32>) -> i32 {
    if vec.len() == 0 {
        panic!("get_first called on empty vector")
    }
    return vec[0].unwrap()
}
\end{lstlisting}

\subsection{Panic vs Error}

\begin{center}
\begin{tabular}{lll}
\textbf{Use} & \textbf{When} & \textbf{Example} \\
\hline
\texttt{Result::Err} & Failure is expected & File not found \\
\texttt{panic!()} & Failure is a bug & Index out of bounds \\
\end{tabular}
\end{center}

\subsection{assert!() for Debug Checks}

Use \texttt{assert!()} to catch programming errors during development:

\begin{lstlisting}
fn process_buffer(buf: *u8, len: u32) {
    assert!(buf != null, "buffer must not be null")
    assert!(len > 0, "length must be positive")
    // ...
}
\end{lstlisting}

Assertions are checked in debug builds. They verify invariants that should always hold if the code is correct.

impl ConfigError {

\section{Showcase: Config Loader}
\label{sec:showcase-config-loader}
% ============================================================================

This complete program demonstrates comprehensive error handling in Novus. It loads configuration files with fallback locations, custom error types, and proper error reporting.

\begin{lstlisting}
// config_loader.novus - Robust Config Loader

from std::core import Option, Result
from std::error::errors import DosError
from std::ffi::dos import Open, Close, Read, Lock, UnLock, Examine
from std::ffi::amiga_consts import MODE_OLDFILE, ACCESS_READ
from std::io::file import print, println

// ----------------------------------------------------------------------------
// Custom Error Type with Rich Information
// ----------------------------------------------------------------------------

pub enum ConfigError {
    FileNotFound,
    ReadFailed(DosError),
    FileTooLarge(u32),
    ParseError(u32),  // Line number
    MissingKey,
    InvalidValue,
    OutOfMemory,
}

impl ConfigError {
    pub fn message(&self) -> *u8 {
        match *self {
            ConfigError::FileNotFound =>
                return "Config file not found in any search location",
            ConfigError::ReadFailed(_) =>
                return "Failed to read config file",
            ConfigError::FileTooLarge(_) =>
                return "Config file exceeds maximum size (64KB)",
            ConfigError::ParseError(_) =>
                return "Syntax error in config file",
            ConfigError::MissingKey =>
                return "Required configuration key is missing",
            ConfigError::InvalidValue =>
                return "Configuration value is invalid",
            ConfigError::OutOfMemory =>
                return "Out of memory loading config",
        }
    }

    pub fn line_number(&self) -> Option<u32> {
        match *self {
            ConfigError::ParseError(line) => Option::Some(line),
            _ => Option::None
        }
    }
}

// ----------------------------------------------------------------------------
// Fallback Chain: Try Multiple Locations
// ----------------------------------------------------------------------------

pub fn load_config(name: *u8) -> Result<Config, ConfigError> {
    var path_buffer = [0u8; 256]

    // Try ENV: first (volatile)
    copy_path(&path_buffer[0], "ENV:", name)
    match try_load_from(&path_buffer[0]) {
        Result::Ok(cfg) => return Result::Ok(cfg),
        Result::Err(_) => {}
    }

    // Try ENVARC: (persistent)
    copy_path(&path_buffer[0], "ENVARC:", name)
    match try_load_from(&path_buffer[0]) {
        Result::Ok(cfg) => return Result::Ok(cfg),
        Result::Err(_) => {}
    }

    // Try S: (startup scripts)
    copy_path(&path_buffer[0], "S:", name)
    match try_load_from(&path_buffer[0]) {
        Result::Ok(cfg) => return Result::Ok(cfg),
        Result::Err(_) => {}
    }

    // Try current directory
    match try_load_from(name) {
        Result::Ok(cfg) => return Result::Ok(cfg),
        Result::Err(e) => return Result::Err(e)
    }
}

% ============================================================================
\section{Summary}
\label{sec:error-summary}
% ============================================================================

\begin{itemize}
    \item \textbf{Use \texttt{Result<T, E>}} for all fallible operations
    \item \textbf{Use \texttt{Option<T>}} when ``not found'' is the only failure mode
    \item \textbf{Pattern match} for explicit handling of all cases
    \item \textbf{Use \texttt{?}} to propagate errors concisely
    \item \textbf{Use \texttt{unwrap\_or}} for safe defaults
    \item \textbf{Avoid \texttt{unwrap()}} except when failure is impossible
    \item \textbf{Use standard errors} (DosError, ExecError, etc.) for AmigaOS operations
    \item \textbf{Use NovusError} when crossing subsystem boundaries
    \item \textbf{Use \texttt{defer}} to ensure cleanup on error paths
    \item \textbf{Use panic} only for invariant violations and bugs
    \item \textbf{Create custom errors} for domain-specific failure modes
\end{itemize}

Error handling in Novus is explicit but ergonomic. The \texttt{?} operator and \texttt{Result} combinators make it easy to write code that correctly handles failures without obscuring the happy path.
